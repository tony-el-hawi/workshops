Mise en situation

Scénario de l'atelier

Le compte à rebours a commencé. Comprendre la mission avant de plonger dans la console.

Vous êtes le data engineer de garde au G.T.R.N. — Global Titan Response Network, l'agence secrète qui traque les monstres géants. Un Titan de Catégorie 3 se déplace sous le Pacifique : les capteurs sismiques s'affolent, les signalements civils affluent, et les satellites détectent des signatures thermiques anormales.

Le Conseil de Sécurité de l'ONU se réunit dans 90 minutes et exige un seul livrable : le Titan Threat Report, un classement des zones côtières par niveau de menace, croisé avec la capacité d'évacuation de chaque ville.

Il n'existe aucun logiciel de tracking de monstres. Il y a juste vous, un déluge de données brutes, et AWS. Le Titan ne surgit pas au hasard : il suit les données. Là où les tremblements se concentrent, où la signature thermique de l'océan grimpe, et où les signalements s'accumulent — c'est là qu'il émergera.

i

Pas de Machine Learning ici. La « prédiction » est un threat score déterministe calculé en SQL — une agrégation pondérée des trois signaux par zone géographique, classée par ordre décroissant. Transparent, reproductible : exactement ce qu'un data engineer livre.

Votre mission : fusionner ces flux disconnectés en un lac de données gouverné, le joindre à la capacité d'évacuation dans l'entrepôt, et exécuter la requête qui produit le classement. Terminez le pipeline — et la ville reçoit son alerte à temps.

Étape 1 · ⏱ 15 min · Ingestion & Transformation

Ingestion temps réel — Kinesis → Lambda → S3

Kinesis Lambda S3

Connectez le flux sismique à votre lac. La Lambda KW-Enrich doit lire le stream Kinesis, géotaguer chaque événement (calcul du grid_cell) et déposer le résultat dans s3://…/bronze/seismic/.

Sous-tâches

  1. Compléter la Lambda KW-Enrich (décodage record, calcul grid_cell, écriture S3).
  2. Configurer le trigger Kinesis sur la Lambda (event source mapping).
  3. Vérifier que les fichiers atterrissent dans bronze/seismic/.
!

Données classifiées : les champs raw_signal_strength et military_sensor_id doivent être conservés tels quels dans Bronze — ils seront masqués plus tard (Étape 6), pas supprimés ici.

★ Flux connecté ! Les événements sismiques enrichis alimentent le lac en continu.

Tâche 1.1 — Compléter la Lambda

  1. Console Lambda → fonction KW-Enrich → onglet Code.
  2. Complétez le calcul du grid_cell (formule partagée avec les données) :
Python
def grid_cell(lat, lon):
    la, lo = int(lat), int(lon)
    ns = "N" if la >= 0 else "S"
    ew = "E" if lo >= 0 else "W"
    return f"{abs(la)}{ns}-{abs(lo)}{ew}"

def lambda_handler(event, context):
    import base64, json, boto3, os
    s3 = boto3.client("s3")
    for record in event["Records"]:
        payload = json.loads(base64.b64decode(record["kinesis"]["data"]))
        payload["grid_cell"] = grid_cell(payload["lat"], payload["lon"])
        key = f"bronze/seismic/{payload['event_id']}.json"
        s3.put_object(Bucket=os.environ["BUCKET_NAME"], Key=key,
                      Body=json.dumps(payload), ContentType="application/json")
    return {"processed": len(event["Records"])}
  1. Cliquez sur Deploy.

Tâche 1.2 — Brancher le trigger Kinesis

  1. Dans la Lambda → Add trigger → Kinesis.
  2. Stream : kaiju-seismic · Batch size : 100 · Starting position : Latest.
  3. Activez le trigger. Le producteur simulé envoie déjà des événements : les objets vont apparaître dans bronze/seismic/.
i

Concept DEA-C01 : l'event source mapping Kinesis→Lambda gère le polling, le batching et le checkpoint pour vous. Batch size et Starting position sont des points d'examen classiques.

Étape 2 · ⏱ 10 min · Data Store

Cataloguer le lac — Glue Crawler

AWS Glue

Un Crawler Glue découvre automatiquement le schéma des trois sources Bronze (seismic, thermal, sightings) et les enregistre comme tables dans le Data Catalog.

Sous-tâches

  1. Créer le Crawler KW-BronzeCrawler sur s3://…/bronze/.
  2. Cible : base de données Glue kaiju_lake.
  3. Lancer et vérifier : 3 tables (seismic, thermal, sightings).
★ Lac catalogué ! Vos données brutes sont désormais interrogeables par schéma.

Tâche 2.1 — Créer et lancer le Crawler

  1. Console AWS Glue → Crawlers → Create crawler.
  2. Nom : KW-BronzeCrawler.
  3. Data source : S3, chemin s3://<bucket>/bronze/ (le crawler découvrira les 3 sous-dossiers).
  4. IAM role : sélectionnez le rôle Glue fourni (KW-GlueRole).
  5. Target database : kaiju_lake.
  6. Create puis Run crawler.

Tâche 2.2 — Vérifier le catalogue

  1. Glue → Data Catalog → Tables → base kaiju_lake.
  2. Confirmez 3 tables (seismic, thermal, sightings) et inspectez leurs colonnes détectées.
i

Concept DEA-C01 : le Crawler infère le schéma et les partitions. C'est le pont entre des fichiers bruts S3 et un accès SQL (Athena/Redshift Spectrum).

3

Étape 3 · ⏱ 20 min · Transformation (cœur)

Transformer — Glue ETL (Bronze → Silver → Gold)

AWS Glue ETLS3 Parquet

Le cœur du pipeline. Un job Glue ETL nettoie le Bronze, le convertit en Parquet partitionné (Silver), puis agrège le threat score par grid_cell (Gold).

Sous-tâches

  1. Bronze → Silver : dédupliquer, filtrer magnitude < 1.0, écrire en Parquet partitionné par grid_cell.
  2. Silver → Gold : joindre les 3 sources sur grid_cell, calculer le threat score, écrire dans gold/threat_scores/.
  3. Lancer le job et vérifier la sortie Gold.
★ Données raffinées ! Le threat score est calculé pour chaque zone.

Tâche 3.1 — Créer le job ETL

  1. Console Glue → ETL jobs → Visual ETL. Nom : KW-Transform.
  2. Sources : 3 nœuds Data Catalog → kaiju_lake.seismic, .thermal, .sightings.
  3. Sur seismic : nœud Filter (magnitude >= 1.0) puis Drop Duplicates.
  4. Nœud Join sur la clé grid_cell (les 3 sources).

Tâche 3.2 — Agréger le threat score (Gold)

Ajoutez un nœud Aggregate (group by grid_cell) ou un nœud SQL Query avec :

Spark SQL · nœud Gold
SELECT
  grid_cell,
  ROUND(0.5 * AVG(magnitude)
      + 0.3 * AVG(temp_delta)
      + 0.2 * (COUNT(sighting_id) / 10.0), 3) AS threat_score,
  ROUND(AVG(magnitude), 2)  AS avg_magnitude,
  ROUND(AVG(temp_delta), 2) AS avg_temp_delta,
  COUNT(sighting_id)        AS sighting_count
FROM joined_signals
GROUP BY grid_cell
  1. Target : S3 s3://<bucket>/gold/threat_scores/, format Parquet.
  2. Save → Run. Surveillez l'exécution dans l'onglet Runs.
★

Concept DEA-C01 : Parquet (columnar) + partitionnement par grid_cell réduisent drastiquement le volume scanné par Athena/Redshift — donc le coût. C'est la bonne pratique d'optimisation testée à l'examen.

Étape 4 · ⏱ 10 min · Operations

Explorer — Athena (SQL ad-hoc)

Amazon Athena

Avant de charger l'entrepôt, menez l'enquête avec Athena : interrogez le lac S3 directement en SQL, sans rien déplacer.

Sous-tâches

  1. Ouvrir Athena sur la base kaiju_lake.
  2. Exécuter les requêtes d'investigation (où le Titan se concentre-t-il ?).
  3. Observer le volume de données scanné (= coût Athena).
★ Enquête menée ! Vous savez déjà où la menace se concentre.

Tâche 4.1 — Requêtes d'investigation

  1. Console Athena → Query editor → base kaiju_lake (configurez un dossier de résultats S3 si demandé).
  2. Top des zones par menace (couche Gold) :
SQL · Athena
SELECT grid_cell, threat_score, avg_magnitude, sighting_count
FROM kaiju_lake.threat_scores
ORDER BY threat_score DESC
LIMIT 10;

Activité sismique brute par zone (couche Silver) :

SQL · Athena
SELECT grid_cell, COUNT(*) AS tremors, ROUND(AVG(magnitude),2) AS avg_mag
FROM kaiju_lake.seismic
GROUP BY grid_cell
ORDER BY tremors DESC;
i

Concept DEA-C01 : Athena facture au volume scanné. Notez la différence de « Data scanned » entre une requête sur Bronze (JSON) et sur Gold (Parquet partitionné) — c'est l'argument clé pour le format columnar.

5

Étape 5 · ⏱ 20 min · Data Store

Entrepôt & rapport — Amazon Redshift

Redshift Serverless

Le moment de vérité. Joignez la couche Gold à la table de référence ref_evacuation dans Redshift pour produire le Titan Threat Report : les villes classées par menace, avec leur temps d'évacuation.

Sous-tâches

  1. Créer un schéma externe (Redshift Spectrum) vers le Glue Data Catalog.
  2. Joindre threat_scores ↔ ref_evacuation sur grid_cell.
  3. Produire le rapport classé par threat_score.
★ Rapport généré ! Le classement d'évacuation est prêt pour l'ONU.

Tâche 5.1 — Schéma externe (Spectrum)

  1. Console Redshift → Query editor v2 → connectez-vous au workgroup Serverless fourni.
  2. Créez un schéma externe pointant vers le Data Catalog :
SQL · Redshift
CREATE EXTERNAL SCHEMA kaiju_lake
FROM DATA CATALOG
DATABASE 'kaiju_lake'
IAM_ROLE default;

Tâche 5.2 — Le Titan Threat Report

SQL · Redshift — la requête finale
SELECT
  t.grid_cell,
  t.threat_score,
  e.city,
  e.population,
  e.evac_capacity_per_hour,
  ROUND(e.population::DECIMAL / e.evac_capacity_per_hour, 1) AS hours_to_evacuate
FROM kaiju_lake.threat_scores t
JOIN ref_evacuation e ON t.grid_cell = e.grid_cell
WHERE t.threat_score > 0.5
ORDER BY t.threat_score DESC;
✓

Si Tokyo Bay (34N-139E) apparaît en tête, votre pipeline est correct de bout en bout ! C'est le contrôle de cohérence du lab.

i

Concept DEA-C01 : Redshift Spectrum interroge des données S3 (couche Gold) sans les charger dans l'entrepôt, et les joint à des tables internes (ref_evacuation). C'est le pattern lakehouse classique de l'examen.

Étape 6 · ⏱ 15 min · Security & Governance

Gouverner — Lake Formation (masquage colonne)

AWS Lake Formation

Les colonnes raw_signal_strength et military_sensor_id sont classifiées. Avec Lake Formation, masquez-les aux analystes junior tout en laissant les senior tout voir.

Sous-tâches

  1. Créer un LF-Tag classification = public | classified.
  2. Tagguer les 2 colonnes sensibles de kaiju_lake.seismic en classified.
  3. Donner au rôle KW-JuniorAnalyst l'accès sauf aux colonnes classified.
  4. Vérifier dans Athena : le junior ne voit plus les colonnes classifiées.
★ Lac gouverné ! Les données militaires sont protégées — mission complète.

Tâche 6.1 — Créer le LF-Tag et tagguer les colonnes

  1. Console Lake Formation → LF-Tags and permissions → Add LF-Tag : clé classification, valeurs public, classified.
  2. Data Catalog → Tables → kaiju_lake.seismic → Edit LF-Tags sur les colonnes raw_signal_strength et military_sensor_id → classification = classified.

Tâche 6.2 — Permissions par rôle

  1. Data lake permissions → Grant.
  2. Principal : KW-JuniorAnalyst · ressource par LF-Tag classification = public → Describe + Select.
  3. Principal : KW-SeniorAnalyst · LF-Tag classification ∈ {public, classified} → Select.

Tâche 6.3 — Vérifier le masquage

  1. Dans Athena (en tant que rôle junior), exécutez :
SQL · Athena (junior)
SELECT * FROM kaiju_lake.seismic LIMIT 5;
  1. Les colonnes raw_signal_strength et military_sensor_id ne doivent pas apparaître dans le résultat.
i

Concept DEA-C01 : les LF-Tags permettent une gouvernance scalable (attribut-based) plutôt que des grants table par table. Le column-level security est un sujet d'examen récurrent.
